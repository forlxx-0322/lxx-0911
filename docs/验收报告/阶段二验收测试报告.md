## 六、本阶段修复的缺陷

| # | 缺陷 | 严重度 | 根因与修复 |
|---|---|---|---|
| 1 | **PUT 更新客户报「名称必填」，更新功能完全不可用** | **高** | 必填校验写在新增/更新分流之前，局部更新（只传等级字段）被误拒。改为：仅在本次提交了 name 字段时才校验，新增路径单独校验 |
| 2 | **数字字段传空字符串导致 HTTP 500** | **高** | 空值被归一为 `null`，而 `reg_capital` 等列是 `NOT NULL DEFAULT 0`，触发数据库约束失败。用户清空「注册资金」即崩。改为按字段类型分流：NOT NULL 数值列归一为 0，仅经纬度允许 NULL |
| 3 | SQLite 中文排序按 UTF-8 字节序，列表按名称排序是乱的 | 中 | SQLite 默认 BINARY 排序（中国→宝钢→新疆）。`node:sqlite` 不支持注册校对规则，改为**两段式查询**：先取 id 在内存按 ICU 拼音排序，再按页取详情。既得正确拼音序又不牺牲性能 |
| 4 | 字典改名后历史数据仍显示旧名 | 中 | 补 `renameInBusinessTables()`，改名时同步刷新 customers/projects/followups/contacts/payments 中的历史值 |
| 5 | 删除自建字典项后再新增同名项会撞唯一约束 | 中 | 软删除行仍占用 `(category,value)` 唯一约束。改为 forceNew 时先把旧行改名为 `__deleted_<id>__<value>` 让出约束 |
| 6 | 修改明细算了但没写入操作日志 | 中 | 补日志写入，并加上字段中文名映射，日志可读为「等级：A → B」 |
| 7 | 曾删除过的选项被复用时提示「已选用已有选项」易误解 | 低 | 改为按「是否已在下拉列表中」判断，不在列表中即提示「已新增」 |

## 七、关键技术决策记录

1. **中文拼音排序**：`node:sqlite` 既不支持 `createFunction`，`db.function()` 也注册不了校对规则（实测报 `no such collation sequence`）。最终方案是两段式查询 + ICU `Intl.Collator('zh-Hans-CN')`。已验证 Node 为**完整 ICU**，拼音序正确。
2. **字段白名单写入**：`CUSTOMER_FIELDS` 等常量定义可写字段，前端多传的字段一律忽略。这是防止 `deleted_at` / `created_at` 被越权篡改的关键。
3. **派生字段由服务层统一维护**：`follow_count` / `last_follow_at` / `next_follow_at` 在跟进增删时自动重算；`deal_amount` 留给阶段三由项目汇总。前端不参与计算，避免数据不一致。
4. **测试可重复性**：所有测试用例自带清理与状态复位，连续运行两次结果完全一致（已实测验证）。字典测试用独立的一次性选项解耦，避免用例间状态依赖。
